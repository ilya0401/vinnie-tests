# Заведение багов из результатов тестов в Jira

## Когда НЕ использовать этот скилл

Красный тест — это ещё не повод заводить баг. По опыту текущего прогона (vinnie-assistant, 2026-10-22): из 7 упавших тестов **6 оказались не багами приложения** — протухший Jira-токен, мёртвый URL сайта, упавший Kafka-контейнер. Только 1 был настоящим дефектом кода (consumer бесконечно ретраит HTTP 400). Если бы на каждое красное падение автоматически летел тикет — получили бы 6 мусорных багов и 1 настоящий, неотличимый от остальных.

Не используй скилл, если причина падения:

- **Сам тест устарел/неправильный** (ждёт поля, которого больше нет; хардкодит ID, которого больше нет) — это **test-automation**, правь тест, не заводи баг.
- **Окружение/инфраструктура**, а не код приложения — протухший токен, не тот URL в `.env.test`, упавший контейнер, временная недоступность Jira/Kafka. Это чинится локально (`docker start`, обновить `.env.test`), в Jira не заводится.
- **Неясно**, что из вышеперечисленного — не гадай и не заводи "на всякий случай". Сначала доведи причину до однозначного ответа (Шаг 1), баг-репорт на "возможно, баг" никому не нужен — его потом закроют как invalid, и это дороже, чем если ты потратишь ещё 10 минут на диагностику сейчас.

## Шаг 1 — триаж: это дефект приложения?

Пройди по порядку, остановись на первом совпадении:

| Вопрос | Если да → |
|---|---|
| Воспроизводится без правок тестового кода, на чистом окружении (валидный токен, все контейнеры живы, актуальный `.env.test`)? | Продолжай триаж |
| Падение исчезает после `docker restart`/обновления конфига/токена, без единой правки кода приложения? | Это инфраструктура. Не баг. Останавливайся |
| Тест ждёт поведение, которого в текущей архитектуре больше нет (например, синхронный ответ там, где теперь асинхронная очередь) — и это осознанное решение, а не то, что сломалось? | Это тест устарел. Правь тест (test-automation), не заводи баг |
| После исключения всего вышеперечисленного падение всё равно воспроизводится детерминированно, и причина — код/логика приложения? | **Это баг. Иди в Шаг 2** |

Если сомневаешься — спроси пользователя, а не решай сам. Ошибка в эту сторону (завёл баг зря) дороже, чем лишний вопрос.

## Шаг 2 — собери bug report по стандартной структуре

Не "коротко опиши проблему" — так теряются детали, без которых баг невозможно воспроизвести позже. Собери явно все поля:

| Поле | Что писать |
|---|---|
| **Title** | Одна строка: компонент + условие падения. "Jira-консьюмер: бесконечный retry на HTTP 400 от log_work", не "баг с джирой" |
| **Component** | Какой сервис/модуль виноват (`vinnie-assistant-jira-consumer`, не весь проект целиком) |
| **Environment** | Где воспроизвели: стек (docker-compose/версии образов), окружение Jira/БД — всё, без чего баг нельзя повторить у себя |
| **Steps to reproduce** | Пронумерованный список, без предположения что читающий знает контекст |
| **Expected / Actual** | Раздельно — что должно произойти и что произошло на самом деле. Не смешивай в одну фразу |
| **Severity** | `blocker` / `high` / `medium` / `low` — честно, по техническому воздействию (роняет весь пайплайн vs косметика), не раздувай и не занижай |
| **Evidence** | Хвост реального лога/стектрейса — не пересказ, а то, что видел сам |
| **Fingerprint-seed** | Короткая стабильная фраза, описывающая **причину**, не конкретный прогон — см. `tools/jira_bug_report/README.md`. Без даты/ID прогона/таймстемпа внутри — иначе дедупликация не сработает и на следующий прогон того же бага тикет задвоится |

## Шаг 3 — черновик и дедупликация, подтверждение у пользователя

Заведение тикета в Jira — видимое другим, не тривиально обратимое действие. **Никогда не вызывай инструмент с `--yes` без явного подтверждения пользователя** — даже если по Шагам 1–2 всё похоже на однозначный баг.

1. Прогони `file` **без** `--yes` (инструмент: `tools/jira_bug_report/`, описание — `tools/jira_bug_report/README.md`):

```bash
python -m tools.jira_bug_report.report_bug file \
    --title "..." --component "..." --environment "..." \
    --steps "1. ..." "2. ..." --expected "..." --actual "..." \
    --severity high --evidence-file /tmp/....log \
    --fingerprint-seed "component:суть-причины"
```

2. Инструмент сам ищет в Jira существующий тикет с тем же fingerprint, **до** показа черновика:
   - **Нашёл** → он не создаёт дубликат и отдаёт ссылку на существующий тикет. Переходи к Шагу 5 (обновление существующего), не к Шагу 4.
   - **Не нашёл** → печатает черновик (title, labels, полный description).
3. Покажи этот черновик пользователю целиком и дождись подтверждения — не сокращай и не пересказывай своими словами, пользователь должен увидеть то же, что уйдёт в Jira.

## Шаг 4 — реальное создание (только после подтверждения)

Повтори ту же команду с `--yes`. Отдай пользователю ключ и ссылку на созданный тикет (`issue_url` из вывода).

## Шаг 5 — что делать при повторном обнаружении того же бага

Если на Шаге 3 инструмент нашёл существующий тикет по fingerprint — **не создавай новый**. Вместо этого:

```bash
python -m tools.jira_bug_report.report_bug comment \
    --issue KAN-23 \
    --text "Воспроизвелось повторно 2026-10-23, прогон <ссылка/ID>, лог: ..."
```

Это общепринятая практика (группировка повторных падений под одним тикетом, а не плодить дубликаты на каждое срабатывание) — трекер остаётся читаемым, а не завален копиями одного и того же.

Когда баг пофикшен и тест, который его поймал, снова зелёный — тоже оставь комментарий на тикете (какой тест и прогон подтвердили фикс), прежде чем пользователь переведёт тикет в Done. Это не автоматизируется этим инструментом (переход статуса — решение человека), но фактическая проверка фикса должна быть зафиксирована на тикете, а не только в чате.

## Самопроверка перед тем как заводить

- Прошёл Шаг 1 целиком и можешь явно сказать, почему это не инфраструктура и не устаревший тест?
- В bug report заполнены все поля из таблицы Шага 2, а не "кратко в одну строку"?
- `--fingerprint-seed` описывает причину, не прогон (без даты/времени/ID запуска внутри)?
- Черновик показан пользователю **целиком** и подтверждён, прежде чем команда ушла с `--yes`?
- Если тикет уже существовал (по fingerprint) — использован `comment`, а не создан дубликат?

## Граница ответственности скилла

Этот скилл заводит баг и останавливается. Забор бага в работу, диагностику, фикс и
PR всегда инициирует человек явно — автоматического claim/skip или фоновой обработки
заведённых багов в проекте больше нет (был заход на это, отказались — см. историю
изменений `tools/jira_bug_report/README.md`).
