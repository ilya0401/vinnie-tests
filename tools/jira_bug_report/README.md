# jira_bug_report

CLI для подачи бага в Jira по результатам прогона автотестов `vinnie-tests`.

Отдельный инструмент, а не часть `tests/` — это не автотест, а разовая команда,
которую запускают (руками или через скилл `jira-bug-reporter`) после того,
как прогон тестов выявил настоящий баг приложения.

## Зачем отдельно от `utils/jira_API.py`

`utils/jira_API.py` — фикстура для тестов, читает worklog'и как часть проверки.
Этот инструмент — создаёт баги, запускается вне pytest, своя зона ответственности
(создание/дедупликация issue, а не проверка существующих данных).

## Переменные окружения

Те же, что уже есть в `.env.test`:

| Переменная | Назначение |
|---|---|
| `JIRA_URL` | база Jira Cloud, например `https://<site>.atlassian.net` |
| `JIRA_API_TOKEN` | API-токен (classic, без scopes — см. automation-log по Jira-интеграции) |
| `JIRA_EMAIL` | опционально, дефолт `iyk040190@gmail.com` |
| `TASK_PREFIX` | ключ проекта в Jira, дефолт `KAN` |

## Дедупликация

Каждый баг помечается в `summary` суффиксом `[fp:<12 hex>]` — коротким стабильным
хэшем от `--fingerprint-seed`. Перед созданием инструмент ищет в Jira тикет
с тем же `fp:` через JQL (`summary ~ "fp:..."`). Если нашёл — не создаёт дубликат,
только показывает ссылку на существующий тикет.

**`--fingerprint-seed` должен описывать ПРИЧИНУ бага, не конкретный прогон** —
иначе дедупликация не сработает:

```
# Хорошо — одна и та же причина опознаётся при каждом повторном появлении:
--fingerprint-seed "jira-consumer:infinite-retry-on-400-logwork"

# Плохо — включает время прогона, фингерпринт каждый раз новый:
--fingerprint-seed "jira-consumer bug on 2026-10-22 15:31:27"
```

## Использование

```bash
# 1) черновик (ничего не создаёт — только показывает, что отправится, и ищет дубликат)
python -m tools.jira_bug_report.report_bug file \
    --title "Jira-консьюмер: бесконечный retry на HTTP 400 от log_work" \
    --component "vinnie-assistant-jira-consumer" \
    --environment "docker-compose local, apache/kafka:4.0.0, Jira Cloud" \
    --steps "1. Создать entry с time_spent=''" "2. Consumer публикует log_work в Jira" \
    --expected "Consumer помечает entry как error и не блокирует очередь (как для 404 not_found)" \
    --actual "Consumer ретраит HTTP 400 бесконечно, блокируя обработку всех следующих сообщений" \
    --severity high \
    --evidence-file /tmp/consumer.log \
    --fingerprint-seed "jira-consumer:infinite-retry-on-400-logwork"

# 2) то же самое, но реально создать тикет
...--yes

# 3) отметить повторное воспроизведение на уже существующем тикете
python -m tools.jira_bug_report.report_bug comment \
    --issue KAN-23 \
    --text "Воспроизвелось повторно 2026-10-23, см. прогон CI #142"
```

Без `--yes` команда `file` всегда работает в режиме предпросмотра — это
осознанная защита от случайного создания тикета (видимое другим, трудно
обратимое действие), а не только рекомендация в скилле поверх него.

## Где заканчивается автоматика

Был заход на автоматический суточный триаж (claim/skip багов по severity +
headless-агент, который сам чинит код и пушит PR). Отказались от этой идеи —
часть про автофикс в принципе не прошла (её заблокировал встроенный
классификатор безопасности Claude Code, `Create Unsafe Agents`), а часть про
claim/skip без реального фикса за ней не несла пользы сама по себе.

Граница ответственности этого инструмента осталась простой: **Claude находит
и заводит баг** (`report_bug.py`), **человек сам инициирует и ведёт фикс** —
без промежуточного слоя автоматического "забора в работу".
